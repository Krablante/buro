# Типы и сохранённые записи

[English](model.md) · [Русский](model.ru.md) · [README](../README.ru.md)

У записи есть `id`, `name`, `kind` и версия `updated_at`, которой управляет BURO.
Содержательные поля определяет выбранный конфиг типа. Неизвестные поля остаются
пустыми; пустые списки не выводятся. Хост, общий корень, описание и запись
текущего контекста не обязательны.

Готовые типы: `project`, `service`, `host`, `item`. Команды `buro types` и
`buro types project` показывают активные определения. Каждый конфиг в `types/`
содержит `id`, необязательный `label` и объект `fields`. Порядок полей задаёт
порядок выдачи. `section` группирует поля; `guide` объясняет их человеку и агенту.
Поля необязательны, если не указано `required: true`.

## Свои определения

```yaml
id: project
label: Мои проекты
fields:
  important:
    type: string-list
    guide: Подтверждённые правила для будущей работы.
```

Это полное допустимое определение, даже если других активных типов нет.
Сохраните его вне установленного пакета и выберите в config.json:

```json
{
  "type_files": ["/path/to/project.yaml", "service", "host", "item"]
}
```

Готовые имена разрешаются внутри пакета, относительные YAML-пути — от каталога
config.json. `buro types copy project <file>` копирует готовое определение,
сохраняя уже существующие файлы. Новый `id` создаёт свой тип. Для каждого id
выбирается один конфиг; наследования и объединения полей между типами нет.
Одноимённые поля разных типов могут иметь разные определения. `default_kind`
задаёт тип по умолчанию; иначе выбирается project, если он есть, или первый тип.

HTTP-клиенты получают определения от сервера реестра. Меняйте и применяйте
их на сервере: type_files в клиентском конфиге не заменяет общую модель.

Форматы полей: `string`, `text`, `boolean`, `integer`, `number`, `ref`,
`string-list`, `record`, `record-list`. У составных полей объявляются вложенные
поля. `ref` ссылается на существующий id и может ограничивать `target_kind`.
Строковый target в `related` может описывать путь или URL без отдельной записи.
Неизвестные поля и неверные значения отклоняются. `packet: false` скрывает поле
из выдачи; `draft_optional: false` убирает отсутствующее поле из черновика.
Данные эти настройки не удаляют. Конфиги не исполняют код и SQL.

Стандартные `locations` содержат необязательные `host`, `path`, `url`, `purpose`.
Новые пути должны быть абсолютными. Если хост отсутствует,
сохраняется текущая машина клиента; это видно в diff. Запись хоста не требуется.
Имена машин должны различаться; при необходимости задайте `current_context`.
Неизвестная принадлежность старого пути сохраняется неизвестной при миграции
и последующих посторонних правках. Укажите host, когда он станет известен.
Неизменённый относительный путь из старых данных тоже сохраняется при другой
правке; при изменении самого местоположения укажите абсолютный путь.
Правила папок можно хранить у хоста, исключения — у конкретного объекта.
Из имени типа геометрия не выводится.

## Применение изменений

Выполните `buro init --dry-run`, затем `buro init`. До применения BURO проверяет
все сохранённые записи и ссылки. Совместимые изменения не требуют ручной
миграции или увеличения общей версии. Правка пояснений не меняет хеш данных.
Удаление заполненного поля, используемого типа или несовместимая смена формата
отклоняются без изменения базы. Верните определение либо явно преобразуйте
экспорт всего реестра и импортируйте его с `--adopt`.
При смене схемы не должно быть активных черновиков. Изменённые миграцией записи
получают новые версии, поэтому старый черновик не перезапишет их.

База хранит применённое определение для миграции и восстановления; это не второй
редактируемый конфиг. Обычное чтение отвергает неприменённую модель. Экспорт
включает модель и записи; сохраняйте резервные копии собственных конфигов.

## Обновление с v1

Исторические starter v2 и politia v5 находятся в `presets/legacy/` для проверки
точных старых привязок. `buro init` переносит `host/path` обычных объектов в
`locations`, а starter `document` — в `item`. Остальные поля и id сохраняются.
Перед применением создаётся снимок SQLite. Предпросмотр не меняет данные и не
создаёт снимок. Экспорт v1 тоже поддерживается: известная старая модель
переносится через `buro import <file> --adopt`.

Прежний полный YAML модели через `preset` или `schema_path` остаётся доступным,
включая необязательный контекст и наборы полей. Полития сохраняет этот формат
для собственного словаря. Для публичной установки он не нужен.
