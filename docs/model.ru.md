# Записи, типы и правки

[English](model.md) · [Русский](model.ru.md) · [README](../README.ru.md)

Одна запись описывает один конкретный объект. Её ID уникален во всей памяти,
постоянен и не выдаётся повторно после удаления. Названия могут совпадать.
Точный ID имеет приоритет перед именем и псевдонимом. Восстановление копии может
вернуть прежний объект с его прежним ID.

## Готовые типы

`project` описывает продукт или самостоятельное дело, в том числе книгу или
исследование. `service` — технический компонент рабочей среды. `host` — компьютер,
сервер или виртуальную машину. Исходники и работающая версия могут оставаться
в одной записи; отдельный сервис полезен, когда компонент обслуживается отдельно.

У всех трёх есть восемь общих необязательных полей:

| Поле | Смысл |
| --- | --- |
| summary | Что это, зачем существует, что делает |
| important | Проверенные факты, решения, требования и условия согласования |
| avoid | Остальные запреты и ограничения работы |
| locations | Исходники, установка, данные, материалы или веб-страницы |
| related | Справочные ссылки на записи, файлы и веб-ресурсы |
| read_first | Основные документы и инструкции |
| aliases | Другие названия для поиска |
| notes | Устойчивые подробности сверх краткого summary |

Условия согласования всегда идут в `important`, включая «не публиковать без
согласия». Дублировать это правило в `avoid` не нужно. У project и service есть
необязательный `repo`. У host — необязательные `addresses` (список строк),
`ssh_target` (строка) и `git_identities` (объекты с полями user_name, user_email,
gh_cli_user и instructions).

Расположение может содержать `host`, `path`, `url` и `purpose`. Новый путь должен
быть абсолютным. Если у нового пути нет host, BURO добавляет устройство клиента;
добавление видно в diff. Запись host необязательна. В related выбирают ровно одно
из `id`, `path`, `url` и при необходимости пояснение `note`. Такие ссылки не
проверяют наличие цели и не мешают удалению. Формат `ref` проверяет и блокирует.

## Свои типы

`buro types new book` печатает путь к временному YAML. Сохраните метаданные
`__buro`, а определение под ними заполните, например, так:

```yaml
id: book
label: Книга
fields:
  editorial_rules:
    type: string-list
    guide: Принятые требования к тексту книги.
  published:
    type: boolean
    guide: Опубликована ли книга.
```

После `buro draft diff <файл>` и `buro draft push <файл>` тип сразу доступен.
`buro types edit book` и `buro types delete book` готовят правки тем же способом.
Используемый тип удалить нельзя. Готовые типы не редактируются и не удаляются;
создайте независимую копию через `types new my-project --from project`.

`--from` берёт коробочный шаблон, даже если после миграции под тем же ID сохранён
свой тип. Когда коробочного нет, копируется действующее пользовательское
определение. Наследования нет; обновления исходного типа не меняют копию.

ID типа постоянен. Необязательную подпись `label` можно менять отдельно. Поля
принадлежат своему типу: одно имя может иметь разные форматы и пояснения в разных
типах. Коробочные поля не подмешиваются в свой тип автоматически.

| Формат | Значение |
| --- | --- |
| string / text | Короткий / развёрнутый текст |
| boolean | YAML true или false |
| integer / number | Безопасное целое / конечное число |
| string-list | Список непустых строк |
| record / record-list | Вложенные поля / список таких объектов |
| ref | ID существующей записи; target_kind при необходимости ограничивает тип |

`guide` объясняет, что сохранять. `required: true` требует значение. `default`
подставляет пропущенное значение. `section` группирует поля в выводе; порядок
берётся из определения. `packet: false` скрывает поле из обычного вывода записи,
но не из хранилища или прямого API. Это не защита секрета. Вложенные поля
описываются так же. Тип без собственных полей допустим.
Если правка типа добавляет значения по умолчанию в прежние записи, они сохраняются
в той же транзакции. Последующая смена default не переписывает эти значения.
Для перенесённых определений `paired_fields` сохраняет прежнее требование
заполнять перечисленные вложенные поля вместе.

Только aliases формата string-list участвует в поиске псевдонимов. Стандартный
locations участвует в списке объектов устройства. Остальные названия полей не
добавляют скрытого поведения. Неизвестные поля и неверные форматы отклоняются.
`buro help` объясняет действующие определения подключённой памяти, включая вложенные.

## Проверяемые правки

`draft new`, `draft pull`, `draft delete` и команды типов выдают каждая свой
временный файл с закрытыми правами доступа. Сохраните служебные метаданные,
отредактируйте содержимое, проверьте `draft diff <файл>` и примените
`draft push <файл>`. Успешный push удаляет только свой файл. Неудачный оставляет
его; `draft clear <файл>` намеренно отбрасывает выбранный черновик.

Diff проверяет ту же операцию, что push. Push повторяет проверку внутри транзакции.
Другие записи могут изменяться параллельно. Изменение версии записи, определения
нужного типа или замена памяти отклоняет устаревший черновик. Получите свежий
и перенесите нужные факты. Просмотр diff не резервирует будущую запись.

Смена kind сохраняет ID. Неподходящие поля нужно явно перенести или удалить;
оставленные неизвестные поля отклонят правку. Удаление значений видно в diff.
Входящие ref, ограниченные прежним типом, блокируют перенос до исправления.
Переименование поля тоже требует явного переноса данных. Массовую замену сначала
проверяют на копии; import заменяет всю память и не служит обходом обычной правки.

## Переход с v2

Остановите API, сохраните предыдущий пакет и снимок, установите v3, посмотрите
`buro init --dry-run`, затем примените `buro init` и перезапустите API. Обновляйте
сервер, общих клиентов и подключения согласованно.

Принятая модель v2 уже хранится в SQLite. V3 разворачивает её в самостоятельные
пользовательские типы под прежними ID, включая project, service, item или lab,
если они есть. ID, значения и версии записей сохраняются. Типы не смешиваются
с новыми шаблонами и не получают их обновлений. Внешние файлы типов и выбор
пресетов больше не используются. После успешного перехода init убирает старые
настройки выбора модели и режима. Единственный черновик v2 не принимается:
сохраните нужные намерения правки и создайте новые файловые черновики.

Поиск псевдонимов v3 использует объявленное поле `aliases` формата string-list.
Если прежний контекст брал имена устройства из другого поля, добавьте aliases
в свой host и перенесите дополнительные имена проверяемыми правками записей.
Значения старого поля сохраняются; произвольные поля не получают скрытого
поведения поиска. Свой прежний тип контекста, отличный от host, остаётся обычным
пользовательским типом.

Для нового шаблона создайте тип с другим ID через `--from` и явно перенесите
записи. Ненужные данные удаляют отдельной проверяемой правкой. Базу без сохранённой
модели сначала нужно открыть и инициализировать через BURO v2 с её исходными
определениями. Экспорты v3 содержат всю действующую модель; пресеты v1 и прежние
форматы экспорта v3 не читает.
