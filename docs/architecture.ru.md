# Архитектура

[English](architecture.md) · [Русский](architecture.ru.md) · [README](../README.ru.md)

У локального или центрального экземпляра BURO один активный пресет и одна
база SQLite. CLI обрабатывает команды и локальный YAML-черновик. Resolver
отвечает за поиск, проверку, вывод, версии и изменение сущностей. HTTP API
обращается к тому же resolver; клиентский режим использует API и не держит
копию базы. Пресет задаёт словарь и представление, SQLite хранит записи
экземпляра.

```text
CLI / draft ─┐
             ├─ resolver ─ схема + пакеты ─ SQLite
HTTP API ────┘                         └──── резервные копии перед записью
                                  ↑
                           активный пресет
```

Сущность занимает одну строку: `id`, `name`, `kind`, `updated_at` и
проверенный JSON-объект полей пресета. По идентификатору и типу можно
запрашивать записи напрямую, не создавая таблицу для каждого словаря. База
привязана к id, версии и SHA-256-хешу контракта пресета. Текст пояснений в
хеш не входит. Изменённую модель нужно явно принять через `buro init` либо
через импорт всего реестра.

Каждое изменение берёт блокировку записи SQLite через `BEGIN IMMEDIATE`,
проверяет версию и объявленные ссылки, создаёт согласованную копию перед
записью и меняет строку. Внутри процесса изменения также сериализуются;
SQLite координирует другие процессы. При ошибке черновик остаётся для
исправления. Импорт проверяет новый набор целиком до атомарной замены строк.

Обычные запросы читают меньше, чем полный экспорт. Прямой поиск берёт одну
строку и записи контекстов для алиасов; `buro list` читает только поля
идентификации; `buro current` — контекст и краткие сведения о его сущностях.
Выборка участников всё ещё просматривает JSON-поля, поскольку поле связи
задаёт пресет. Полный перечень записей нужен для экспорта и явного запроса
`/entities`. Резервная копия делается при каждом изменении, поэтому цена
записи растёт вместе с базой: BURO рассчитан на проверяемые, сравнительно
редкие изменения фактов, а не на поток событий.
