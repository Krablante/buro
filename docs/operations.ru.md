# Настройки и эксплуатация

[English](operations.md) · [Русский](operations.ru.md) · [README](../README.ru.md)

Локальная работа не требует сервера и ручной настройки. `buro init` создаёт
SQLite и, если файла нет, небольшой config.json с готовыми типами. Изменяемые
данные находятся вне установленного пакета:

```text
~/.config/buro/config.json
~/.local/share/buro/
  BURO_DRAFT.yaml                 # во время правки
  state/buro/buro.sqlite3
  state/buro/backups/sqlite/
```

Настройки программы и YAML-определения типов независимы. Выбор типов описан
в [модели](model.ru.md). Local открывает SQLite, central добавляет HTTP,
client обращается к тому же реестру через HTTP и не хранит копию базы.
Клиенту достаточно:

```json
{
  "api_url": "http://registry:8765",
  "current_context": "worker-a"
}
```

API URL подразумевает client, если mode не задан явно. Имя машины по умолчанию
— короткий hostname. Если имена совпадают, задайте разные `current_context`.
Запись host необязательна: она хранит общие правила машины и существующий корень.

`BURO_CONFIG` выбирает config.json; переменные окружения имеют приоритет над
JSON. `type_files` выбирает готовые имена или YAML-пути, `default_kind` — тип
по умолчанию. Эти два параметра задаются в JSON. Старые полные модели через
`preset` / `schema_path` сохраняются; явный type_files имеет приоритет.

| Ключ JSON | Переменная |
| --- | --- |
| mode | BURO_MODE |
| current_context | BURO_CURRENT_CONTEXT |
| api_url | BURO_API_URL |
| central_host | BURO_CENTRAL_HOST |
| instance_root | BURO_ROOT |
| state_dir | BURO_STATE_DIR |
| database_path | BURO_DATABASE_PATH |
| backup_dir | BURO_BACKUP_DIR |
| backup_retention | BURO_BACKUP_RETENTION |
| draft_path | BURO_DRAFT_PATH |
| preset | BURO_PRESET |
| schema_path | BURO_SCHEMA_PATH |

`buro backup` использует online backup API SQLite. Перед изменениями и
применением модели сохраняется снимок; предпросмотр снимок не создаёт.
По умолчанию остаются последние 20. `init` без изменений не создаёт снимок.
Новые базы и снимки создаются с правами 0600; существующие права сохраняются.
Копируется вся база: частые изменения
большого реестра расходуют I/O и место. События и разговоры храните отдельно.
Восстановление проверяйте в другом экземпляре через экспорт/импорт или снимок.

При обновлении установите пакет, проверьте `buro init --dry-run`, выполните
`buro init` и обновите подключение агента. Центральный API остановите на время
применения новой модели, затем перезапустите и обновите клиентов. Известные
модели v1 переносятся с сохранением записей. До проверки API и клиентов храните
прежний пакет и снимок. Не восстанавливайте базу, пока в неё идёт запись.

`init`, `backup`, `export`, `import`, `serve` требуют прямого хранилища.
У HTTP нет авторизации и TLS: используйте loopback, доверенную частную сеть
или защищённый proxy. Клиенты не копируют и не открывают центральный SQLite.

## Развёртывание Политии

`npm run deploy:politia` (также `deploy:live`) обновляет существующие центральную
установку и клиенты Политии на Linux. Он проверяет применение модели, собирает
один пакет, останавливает API, сохраняет прежний пакет и снимок, затем обновляет
центральную установку. Возможность отката сохраняется до успешной проверки
установленного CLI и HTTP. Workers получают те же байты. Настройки хостов,
включая собственные endpoints и пути черновиков, остаются на месте. Нужны
работающие SSH, sudo, Node и пользовательский unit `buro-api.service`.
Используются настройки центрального хоста; ffmpeg для развёртывания не нужен.
Изменение исходников не обновляет установленную программу. Перед применением
вне Политии прочитайте скрипт.

```sh
npm run deploy:politia -- --dry-run
npm run deploy:politia
```

Недоступный worker остаётся pending; ошибка доступного хоста проваливает deploy.
Каждый запуск сохраняет пакет, материалы отката и `pending.json` в
`<state_dir>/deployments/<version>-<timestamp>/`. Файл содержит контрольную сумму
пакета и результаты обновления хостов. Храните материалы до завершения rollout;
на вернувшийся хост установите сохранённый пакет. Скрипт обновляет подключение
OpenCodez; изменённый код плагина требует перезапуска клиента.

`BURO_SOURCE_ROOT` выбирает checkout; `BURO_ROOT` по-прежнему выбирает данные.
`PACK_DIR` меняет место артефактов. `BURO_WORKER_HOSTS` ограничивает развёртывание
списком SSH-имён через пробел; иначе машины берутся из реестра.
`BURO_WORKER_PREFIX` по умолчанию равен `/usr`; центральный prefix — `/usr/local`.
`--skip-workers` обновляет только центр. Терминальные демонстрации описаны
в [разработке](development.ru.md) и не связаны с развёртыванием runtime.

## Восстановление и частые ошибки

Сначала проверьте восстановление в отдельном экземпляре. Выберите те же
определения и отдельный каталог данных, создайте базу и импортируйте экспорт:

```sh
BURO_CONFIG=/path/to/recovery/config.json BURO_ROOT=/path/to/recovery/data buro init
BURO_CONFIG=/path/to/recovery/config.json BURO_ROOT=/path/to/recovery/data buro import /path/to/export.yaml
BURO_CONFIG=/path/to/recovery/config.json BURO_ROOT=/path/to/recovery/data buro list
```

Для собственных типов создайте настройки восстановления до инициализации.
`type_files` должен указывать на сохранённые определения. Альтернатива — сохранить
объект `model` из экспорта в отдельный YAML и выбрать его через `schema_path`.
Снимок SQLite можно поставить на место целевой базы при остановленных API и
процессах записи. Перед запуском сервиса проверьте `buro list` и известную запись.

| Симптом | Что делать |
| --- | --- |
| Модель не применена / другой хеш | Посмотрите `init --dry-run`; если он отклоняет сохранённые поля, восстановите определение. |
| Черновик уже существует | Откройте указанный файл; завершите или сохраните правки перед `draft clear`. |
| Конфликт ревизии | Сохраните правки, получите свежий черновик и сравните с текущей записью. |
| API недоступен / timeout | Проверьте URL клиента и `/health` сервера. Черновик остаётся; перед повторной записью прочитайте запись. |
| Агент игнорирует BURO | Проверьте `buro` в терминале агента, обновите подключение и начните новую сессию. |
